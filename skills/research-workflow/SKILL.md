# 研究文档协作

把研究文档作为共同工作的界面：呈现目标、计划、发现和待讨论问题，让用户直接编辑或评论；在下一阶段开始及恢复执行前同步最新反馈，写明处理结果，再调整研究。研究方法和资料工具随任务选择，无浏览器、多 Agent 或交互卡片前置依赖。

开始时创建或关联用户授权的研究文档。使用已安装的飞书文档工具（本仓库提供 `lark-docs`），先查实际 CLI help 确认正文与分页评论读取能力。不能用研究启动请求推断额外分享权限。已有文档保留用户内容；新文档可采用 [研究模板](assets/research.md)。

用任务独有的本地目录保存必要的原始读回和研究产物。读取 [反馈与恢复协议](references/protocol.md)，以飞书文档正文和评论为唯一协作状态；不要求额外的任务状态机或文件索引。脚本不调用飞书、不启动调度、不创建群聊；工具调用由执行 agent 完成，群聊/会话编排由 #4754 承接。

每轮协作：

1. 获取完整正文和全部评论（包括新增回复），保留原始响应。使用已安装的 `lark-cli docs +fetch --doc TOKEN --doc-format markdown --scope full --as user|bot`，再用 `lark-cli drive +list-comments` 和 `+list-replies` 读取所有分页；记录成功读回的时间和正文版本。只有转换已保存的旧响应时使用 `scripts/feishu-snapshot.mjs`，不为旧响应补造当前时间；不要经 shell 文本输出或手工抄写重建。读取失败或分页不完整时保留上次成功读回，说明未同步，暂停依赖这些反馈的阶段。
2. 先检查上次写回是否已在完整读回中出现。若写回结果不明确，先比较正文和版本，再决定确认、补写或保留为待核对；不要盲目重试追加。结合正文上下文解释用户意图；对待澄清的意见在文档中明确提问，不自行把等待算作回答。
3. 根据已读取的意见推进本轮研究，将计划、证据或结论的实质改动增量写入文档，保留用户内容。实质更新后重新完整读回，结合本轮实际改动核对，不把自己刚写的正文误当作用户新要求，也不忽略同时出现的用户编辑或评论。
4. 对已核对的意见，在文档中直接写明采纳、待澄清或未采纳及理由，并在下一次完整读回中确认。回执说明不能替代真实研究更新。
5. 每轮结束都基于完整读回核对正文、版本、评论和研究是否仍在进行。新反馈能在本轮处理则处理；来不及或需用户回答时保留为待处理并明确说明，不能宣称已全部同步处理。不要为消除待处理项重复改写相同结论。取消时保留文档与产物。

本轮结束时，在聊天中给出当前研究文档的可点击链接，简述已确认的变化、未解决信息及研究是否仍在进行。内部读回记录留在任务私有目录，不作为用户的操作入口。

仅本地检查点通过不能宣称真实飞书协作通过。交付时分别记录代码/fixture 测试和真实用户文档反馈的证据。

更新入口状态、范围或时间等文字时，用 `scripts/write-feishu-text.mjs` 从 JSON stdin 接收原文并调用 CLI，避免 shell 解释反引号、`$()` 或换行。读取与安全写入示例见[采集时间与文字写入](references/protocol.md#collection-time-and-literal-writes)。显示时间引用成功读回的时间和对应正文版本；不要把写入时间当作采集时间。无成功读回时间时明确未知，不制造时间。
