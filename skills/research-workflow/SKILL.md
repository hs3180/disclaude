# 已有研究检查点兼容维护

先确认任务已有本协议生成的状态文件（包含 `schema: 1`、`taskId`、`documentId`、`pendingWrite` 等字段），或用户明确要求使用旧协议。文件名不是判定依据；不要因为任务涉及研究、飞书文档或“继续”就初始化此协议。

新任务使用已有项目文件约定与通用执行能力；目录中提供 `project-work` 时使用它接续任务内容，文档读写使用实际可用的文档工具。飞书文档展示研究内容、证据、用户意见及实质修订，聊天提供入口和讨论。新任务不创建本协议状态、不要求固定阶段，不向文档追加机器生成的 `Feedback checkpoint`、操作 ID、反馈键或哈希。已有其他任务记录不迁移到本协议，也不另建重复账本。

下文只适用于已确认的旧协议任务。保留原任务身份、文档绑定、反馈与未知写入记录，不自动搬移或删除。研究方法和资料工具仍随任务选择，无浏览器、多 Agent 或卡片前置依赖。使用已安装的文档工具，先核对实际 CLI 的正文与完整分页评论读取能力；已有授权和用户内容保持有效，不推断额外分享权限。

沿用原任务目录中的检查点和产物。读取 [反馈与恢复协议](references/protocol.md)，使用 `scripts/state.mjs` 管理任务/文档绑定、反馈和写回状态。脚本不调用飞书、不启动调度、不创建群聊；工具调用由执行 agent 完成，群聊/会话编排由 #4754 承接。

旧协议任务的每轮协作：

1. 获取完整正文和全部评论（包括新增回复），保留原始响应；规范化为协议中的 snapshot。读取失败或分页不完整时保留旧检查点，说明未同步，暂停依赖这些反馈的阶段。
2. `sync` 识别正文变化和新增/编辑评论；结合正文上下文解释用户意图。对待澄清的意见在文档中明确提问，不自行把等待算作回答。
3. 通过 `prepare` 记录拟采纳、待澄清或未采纳意见及理由。检查最新正文仍与准备版本一致，然后把返回的 fragment 追加到文档；不整篇替换。把研究计划/结论的实质改动另作增量更新，并在下一次 sync 核对。
4. 重新完整读取文档，`ack` 确认写回后才把反馈标为已处理；并发编辑、未知写入或重启后的恢复按协议执行。若正文格式规范化导致 `write_not_observed`，先检查既有片段并保留待核对状态，不为获得成功回执反复追加；未能确认时向用户简短说明未同步，停止进一步回执写入。反馈状态是处理记录，不能替代真正补充证据或修改研究结论。
5. 未解决反馈处理后推进研究阶段；完成前再次同步，保留结论、来源、分歧和反馈记录。取消只停止后续执行，保留文档与产物。

仅本地检查点通过不能宣称真实飞书协作通过。交付时分别记录代码/fixture 测试和真实用户文档反馈的证据。
