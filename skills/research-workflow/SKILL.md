# 研究文档协作

把研究文档作为共同工作的界面：呈现目标、计划、发现和待讨论问题，让用户直接编辑或评论；在下一阶段开始及恢复执行前同步最新反馈，写明处理结果，再调整研究。研究方法和资料工具随任务选择，无浏览器、多 Agent 或交互卡片前置依赖。

开始时创建或关联用户授权的研究文档。使用已安装的飞书文档工具（本仓库提供 `lark-docs`），先查实际 CLI help 确认正文与分页评论读取能力。不能用研究启动请求推断额外分享权限。已有文档保留用户内容；新文档可采用 [研究模板](assets/research.md)。

修订当前结论前，先把将被替换的旧结论原文（包括前提、限制及原有引用）保存在同一文档的历史区，标明原版本或日期，并读回确认，再更新当前段落。同一版本已经保留则不重复追加。核验历史时比对实际旧段，不能用“旧结论已保留”这句话代替证据；若旧段已经缺失，只从可核对的旧快照或原报告恢复，不凭记忆补写。

每次替换都包括当前即将被覆盖的最近版本，不能只补最早一版。按[结论保留核验](references/conclusion-history.md)，把实际替换的原段和完整读回交给 `scripts/verify-conclusion-history.mjs` 逐字检查；失败时不能宣称历史完整。

用户应能从飞书文档查看支撑结论的产物。关键实验的完整脚本、运行条件和观察结果可直接放入文档；较大产物使用已有附件能力提供用户可访问的链接。不要只给本地绝对/相对路径或仅在项目目录存在的 Markdown 链接。发布前核对所给入口确实包含产物，而不是只描述它已保存。

用任务独有的本地目录保存检查点和产物。读取 [反馈与恢复协议](references/protocol.md)，使用 `scripts/state.mjs` 管理任务/文档绑定、反馈和写回状态。脚本不调用飞书、不启动调度、不创建群聊；工具调用由执行 agent 完成，群聊/会话编排由 #4754 承接。

每轮协作：

1. 获取完整正文和全部评论（包括新增回复），保留原始响应；使用 `scripts/feishu-snapshot.mjs` 从原始 CLI JSON 响应生成 snapshot，保留正文与评论字符串并沿用固定评论/回复 ID 映射。正文中的评论引用不能替代评论接口；不要经 shell 文本输出或手工抄写重建。读取失败或分页不完整时保留旧检查点，说明未同步，暂停依赖这些反馈的阶段。
2. 先检查保存的 `pendingWrite`。存在未确认写入时，先用完整读回尝试 `ack` 确认原操作；只有回执缺失、正文冲突或评论变化导致确认失败时才按协议 `reconcile`，不要先 `sync` 或重试追加。处理后再用 `sync` 识别正文变化和新增/编辑评论，结合正文上下文解释用户意图。对待澄清的意见在文档中明确提问，不自行把等待算作回答。
3. 根据已读取的意见推进本轮研究，将计划、证据或结论的实质改动增量写入文档，保留用户内容。实质更新后重新完整读回并 `sync`；自己刚写的正文也会进入待处理记录，结合本轮实际改动核对，不把它当作用户又提出了新要求，也不忽略同时出现的用户编辑或评论。

   实质修订完成后，使文档开头的当前状态、推荐与下一步反映最新结果，并注明更新依据和时间；不能只在末尾追加新结论而让入口仍展示旧状态。保留原始材料、用户原文和历史结论，将历史与当前判断明确区分。针对最新读取的相关块增量修改；当前区与用户编辑冲突时保留双方内容、说明冲突，不宣称已同步。回读时同时核对入口摘要和详细修订是否一致。

4. 对已核对的待处理项，通过 `prepare` 记录采纳、待澄清或未采纳及理由。用 `state.mjs receipt <state-file> <version>` 直接导出原片段；不要手抄回执、键及操作 ID。检查最新正文仍与准备版本一致，导出成功后追加一次，再完整读回并 `ack`。从 `prepare` 到 `ack` 之间不穿插实质正文修改；回执确认不能替代真实研究更新。
5. 每轮结束都基于完整读回同步检查点，即使研究仍在进行。最后的完整读回若已成功 `ack` 且之后未再修改文档，可直接用于收尾核对；否则重新读取并 `sync`。核对检查点正文/版本与最后读回一致，并检查待写入、待处理反馈和待澄清项。新反馈能在本轮处理则按上述顺序处理；来不及或需用户回答时保存为待处理并明确说明，不能宣称已全部同步处理。不要为消除待处理项重复改写相同结论。改变阶段或 `finish` 仍须满足协议条件；取消保留文档与产物。


本轮结束时，在聊天中给出当前研究文档的可点击链接，简述已确认的变化、未解决信息及研究是否仍在进行。用“已确认反馈记录”等用户可理解的结果描述恢复；`ack`、`sync`、检查点版本和内部操作 ID 留在本地记录，不作为用户的操作入口。 本地检查点路径也不作为飞书中的用户入口。

仅本地检查点通过不能宣称真实飞书协作通过。交付时分别记录代码/fixture 测试和真实用户文档反馈的证据。
