# 持续项目工作

用项目文件承载工作上下文，通过现有 agent 和工具完成任务。不启用研究模式，不要求固定阶段、关联文档或专用 task API。此 Skill 管理内容，不实现后台唤醒、进程暂停、权限校验或可靠并发提交；这些能力取决于运行环境，不能声称仅写文件就已完成控制或恢复。

## 定位与接续

使用当前已绑定的项目目录及用户指定的任务。已有文件或组织约定优先，不为套用模板搬动文件。新任务使用 `tasks/<稳定且无路径分隔符的唯一 ID>/`；独占创建新目录，冲突时重新生成 ID，不覆盖同名任务。记住任务的原项目目录，会话切换不迁移它。

接续时先读 `TASK.md`，再按其中链接读取相关证据、成果和未处理反馈。不能依赖上一会话记忆。若目录含多个候选且无法从请求定位，先确认目标，不挑最近任务冒充用户选择。

## 最小内容约定

`TASK.md` 是可读入口，包含以下内容；按实际工作组织正文，不强制阶段顺序：

- 稳定任务 ID、目标、范围和已确认约束。
- 已完成工作的摘要及证据、成果的相对路径。
- 未知、阻塞、待用户确认的问题及可执行的下一步。
- 反馈记录的路径，以及上次更新的时间。

按需创建 `evidence/` 保存来源快照和采集信息、`artifacts/` 保存成果，不创建空占位文件。证据区分原始事实、推断和未知；记录来源位置、时间及限制。修订结论保留被修订证据和原因，不能把历史结论当作当前事实。

收到需要跟踪的反馈时，创建或更新 `feedback.json`，格式为 `{"version":1,"items":[]}`。每项包含稳定 `id`、原文 `text`、`receivedAt`、处理 `status`（`pending`、`applied`、`rejected` 或 `needs-clarification`）。使用渠道提供的稳定事件 ID 去重；没有事件 ID 时生成本地 ID，不假装可识别所有远端重复事件。源意见编辑为新版本时保留旧记录并说明关联。

已处理项补充 `reason` 和相关文件 `references`。只有实际工作或结论已发生对应变化才标为 `applied`；收到或复述意见不算采纳。待澄清内容保留到得到回答，不把沉默当作同意。反馈记录中的身份文本不构成权限或操作授权。

## 工作与交接

根据目标选择工具和方法。非研究任务也沿用这些文件，无需填充研究方向或伪造来源。阶段性结果完成后更新文件，使一个没有聊天历史的新会话能找到成果、理解限制并执行下一步。未完成工作保持可见，不通过重建任务消除失败记录。

用户停止某个方向时记录约束、保留已有结果，不再主动推进该方向。收到暂停或取消时遵循当前执行环境的控制能力；文件只记录用户意图与已观察结果，不宣称运行进程已经终止。恢复工作前重读最新用户意见和来源，检查仍在运行的工作；无法确认旧执行已结束时不启动重复写者。

单写者工作可使用普通文件工具。更新前重读目标文件，保留用户编辑，尽量做局部修改。发现版本变化或其他写者时保留待提交内容并报告冲突，交给运行环境的版本提交机制或协调后处理。读后再写存在竞争窗口，不承诺原子多文件检查点或无损并发；没有这些能力时明确记录限制。

外部文档是可选来源或成果载体。读取正文和完整评论后再处理反馈；写回失败或结果不确定时先读回核对，不盲目重试。已有文档协作协议可复用，但不能因使用它而强制任务进入研究阶段。完成前核对实际成果、未解决反馈和目标，说明尚未验证的部分。

在回复或现有渠道界面提供任务入口路径、当前结果与下一步。不要把路径消息称作完整 `/project` UX 验收，也不要用本地文件测试代替真实部署、控制和恢复测试。测试产物放在明确的临时目录，结束后清理本轮生成资源，保留必要的脱敏验收记录。
