## 可复现观察

### 1. 创建、绑定和启动路径可以到达

真实聊天中，候选服务在当前 Project 创建并持久化了 Research 记录，随后报告 `paused` → `running`，并通过 Feishu 聊天发送了状态更新。Project、聊天和文档绑定均可在状态文件与 `get` 结果中核对。这只证明入口和状态初始化到达，不能证明研究回合、文档写回或恢复完成。

### 2. 默认运行：没有 checkpoint

第一次真实启动使用默认 stall 配置，研究回合运行约 `216.614s` 后结束。服务日志记录：

- `toolCallCount=0`；
- `hadError=false`；
- SDK stream 已结束，但没有可持久化 checkpoint；
- 状态变为 `failed`、revision `4`、`stepCount=0`；
- error 为 `Research turn returned no checkpoint.`；
- directions/findings 为 `0/0`；
- 文档仍为 revision `3`、`publishedFragments=0`，正文没有写回。

这不是文档权限或分页失败：文档在启动前后都成功完整读取，且失败发生在研究结果持久化之前。

### 3. 单次恢复：延长 watchdog 后暴露 checkpoint schema 拒绝

按真实聊天要求，先以最新 revision 读取并只执行一次 `resume`，不创建新项目、方向或反馈。诊断运行只把本次候选进程的 stall timeout 提高到 `600s`，使用同一模型、Project、聊天和文档。

该回合运行约 `978.615s`，服务日志记录 `toolCallCount=27`、SDK turn 完成并返回了结果；因此第一次“空 checkpoint”不能单独解释整个失败。结果随后在 checkpoint 校验处被拒绝：

```
Research checkpoint work[0].findings must contain at most 4 items
```

最终持久化状态为：

| 字段 | 值 |
| --- | --- |
| status | `failed` |
| revision | `7` |
| stepCount | `0` |
| directions / findings | `0 / 0` |
| document revision | `3` |
| published fragments | `0` |
| error | `Research checkpoint work[0].findings must contain at most 4 items` |

真实 Feishu 聊天收到最终 `failed` 状态；再次完整读取文档仍得到 revision `3` 和未改变的初始正文，没有任何发现、来源、不确定性、反馈处理或修订记录被写回。

## 发现与未决问题

1. 研究入口、Project 绑定、状态初始化和 Feishu 状态通知是可达的；Research 主路径尚未通过真实验收。
2. 默认运行存在“没有 checkpoint”的失败路径。其运行时长与默认 stall watchdog 窗口相符，但仅凭这一轮不能把所有原因归结为 watchdog；需要在修复 PR 中用明确的超时/中断回归证据区分。
3. 延长 watchdog 后，真实模型结果能够走到 checkpoint 校验，但返回的单个 work item 包含超过四条 findings，现有边界把它作为失败而不是安全地分段、汇总或要求模型继续。该 hard limit 是第二个独立的实时阻断点。
4. 长时间恢复期间，Feishu 发起消息使用的短期隐藏 context 在服务端过期；期间通过 bridge 的状态读取明确返回 `Research context expired; continue from the current chat message.`。这使“离开后重返”和长运行状态查询仍未被证明，且不能靠把失败隐藏成 running 来规避。
5. 文档未写回并非验收通过，而是上述研究回合未产出可接受 checkpoint 的直接后果。
6. 旧候选的独立 Research store/manager/CLI/card 设计不符合维护者关于复用原 Project 的反馈；本记录不能授权继续沿用该架构。
