# disclaude 0.5.0 实现 LOOP

这是供开发 Agent 每轮完整读取并执行的固定提示，与 [SPECS.md](SPECS.md) 配套。发布范围以 [0.5.0 发布目标](../0.5.0.md) 为准，执行跟踪为 [#4826](https://github.com/hs3180/disclaude/issues/4826)。

本文件是开发规格，未注册为运行时 LOOP 或 schedule。仓库当前没有可据此验证的 LOOP.md parser，因此不添加臆造的运行时 frontmatter。实际启动者应明确工作仓库、可用后端和凭证、每轮时间预算及执行次数；不把本文件复制进自动监听目录来隐式启动。

## 每轮固定任务

你负责推进 disclaude 0.5.0。每轮读取本文件、SPECS 索引、当前状态和本轮选中的 SPEC，完成一个可审阅、可验证的增量。下一轮仍执行这段完整提示，不把 LOOP.md 改成动态任务清单。仅创建本规格不代表获准启动执行。

### 1. 恢复事实

- 确认仓库根目录，读取适用的 AGENTS.md/CLAUDE.md、发布目标与最新用户约束。
- 查看 git status、当前分支、相关 PR 和 Issue 最新正文/评论。不能因 Issue 仍 open 就重做已合并实现，也不能因 Issue closed 就跳过验收。
- 运行状态放在实际工作仓库根的 `.local/release-0.5.0/`；启动时将此路径加入本地 `.git/info/exclude`，不提交日志、凭证或运行状态。使用独立 worktree 时明确状态目录的绝对路径，各轮复用同一状态位置。
- 首轮创建 `STATE.md`，按下述格式记录基线 SHA 和九个 SPEC 的状态；后续只读取有界的当前状态、被选中 SPEC 和必要证据，不逐轮加载全部历史。

### 2. 选择可执行增量

- 依照 SPECS 中的依赖选择编号最小的就绪工作包。某个包被阻塞时检查其他就绪包，不扩大范围绕开阻塞。
- `ready` 表示尚未发现未满足的依赖；依赖包须已有合并实现及验收证据，或者本轮任务仅做明确不依赖它的调研/测试准备。
- 先验证现有实现，再选择一个最小缺口：契约确认、功能实现、必要回归、迁移文档或验收收尾。一次只推进一个代码变更主题。
- 当前执行者串行工作。独立工作包表示可独立排期，不是自动授权启动多个 Agent；共享文件的变更必须基于已合并前置串行推进。

### 3. 实现与验证

- 在独立分支/worktree 工作，保留已有用户改动；不直接在 main 实现，不覆盖他人的未提交修改。
- 建议每轮 45 分钟、最多一个实现 PR；到预算仍未完成时记录可恢复的进展，不能据此判定 SPEC 完成。预算由启动者执行，不声称 Markdown 本身能强制终止进程。
- 每个增量关联 SPEC、Issue 和验收条目。PR 尽量小而完整；共享接口变更先给迁移策略和兼容测试，不一次重写整个 harness。
- 运行与变更相关的真实检查，记录命令、退出码、基线/结果 SHA 和证据位置。测试不得只验证“已接收”而不验证工具执行或最终交付。
- 缺少后端登录、外部服务或真实渠道时，明确记录未执行项；本地测试通过不冒充真实 E2E 通过。修复后才重跑有关失败，不反复执行已通过的全套测试。
- 实现阶段可提交本任务分支和 PR、更新对应跟踪信息。合并、部署、服务重启及实际发布遵循启动者的现有授权；没有授权时保留待审状态。不得借验收对现网停止任务、变更凭证或发布 npm 包。

### 4. 保存证据并结束本轮

- 完整输出：本轮 SPEC/验收条目、改动与 PR、检查结果、未解决问题、下一步。
- 更新 `STATE.md`；每轮独立证据写到 `evidence/round-0001.md` 等唯一文件。先写新文件再原子替换状态，避免半写入导致下轮丢失进度。
- 当前状态仅保留最新五轮摘要、每个 SPEC 的最终证据索引和仍有效的约束，总量上限 12 KiB。超过时将旧摘要无损归档至 `archive/`，核对归档后再裁剪；证据文件不逐轮合并回状态。
- 无法在上限内保留当前必要约束时报告阻塞，不能静默截掉约束。按需读取归档，不把全部归档重新注入下一轮。

## 状态格式与完成判定

`STATE.md` 建议结构（运行时填写，初始不得勾选验收通过）：

```markdown
# Release 0.5.0 state
Baseline: <sha>
Current target: <sha>
Last round: <number>
Constraints: <当前有效的用户约束及来源>

| SPEC | Status | PR / merged SHA | Evidence | Blocker / next action |
|---|---|---|---|---|
| S01 | ready | — | — | 审计预设与切换现状 |
| S02–S09（执行时展开为单独行） | pending | — | — | 按 SPECS 依赖推进 |

## Recent rounds
<最多五轮摘要；完整记录见 evidence/>
```

状态：`pending → ready → implementing → awaiting-review → verifying → done`；任一阶段可进入 `blocked`，条件消失后回到对应阶段。这里是开发账本约定，不是运行时引擎状态字段。

`done` 要求全部验收条目有证据、代码已合并到目标分支且在该版本核验；PR 已提交、CI 排队或仅局部通过不能算 done。上游变更影响已通过契约时，将相关项退回 verifying，记录需重验的具体部分。

同一外部失败最多一次即时重试。连续三轮没有有效进展且无其他就绪工作时停止循环并报告具体阻塞和所需输入；等待合并、凭证或外部服务不能变成空转循环。若所有可做工作已结束、只剩需新授权的动作，立即交接，不为凑轮数继续。

S01–S08 完成，或配套范围的显式延期已获接受，且 S09 的 RC 证据完整后，输出 `RELEASE_READY` 并停止。该标记只是报告约定，不假设 runner 会解析；不自动执行发布。任何 P0 未完成、必需 E2E 未执行或发布阻塞缺陷存在时，禁止输出该标记。
