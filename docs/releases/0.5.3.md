## Version position

**Deterministic skill resolution and truthful terminal delivery.**

Skills are resolved once through a verifiable trust boundary and consumed consistently by each harness. Runtime failures, task completion, and command schedules provide correct terminal behavior rather than misleading recovery or extra chat noise.

## P0 release goals

### 1. One trusted Skill resolution path

Deliver a harness-neutral registry, exported by `@disclaude/core`, as the source of truth for discovery, precedence, metadata validation, filesystem trust, and diagnostics. Connect Codex as its first consumer without losing project-local skills; keep source-layout and transport configuration outside the shared core.

- #4908: unified `SkillsRegistry` core
- #4910: trust-boundary and hostile/malformed-resource hardening
- #4909: one resolved manifest for Codex exec and app-server
- #4992: resolve project root separately from transient chat workspace

Acceptance:

- Codex exec and app-server expose the same resolved manifest for a given project/configuration.
- A project-local skill remains visible when the state workspace is elsewhere; model-facing manifest references are safe and never rely on an absolute host path.
- Malformed frontmatter, unsafe paths, and untrusted resources fail closed with actionable diagnostics; they cannot escape configured roots or silently alter the manifest.
- Codex regressions cover project/user/builtin precedence, root separation, transport parity, and invalid resources.

### 2. Truthful terminal delivery and managed command execution

Make task completion, error recovery, and scheduled child commands match the state the user sees.

- #4989: persistent runtime errors do not enter reconnect/backoff or consume retry budget
- #4984: command schedules inherit the live managed REST endpoint and authentication context
- #4907: use a completion reaction on the actual final delivery instead of a standalone `✅ Complete` message

Acceptance:

- Non-transient errors yield one actionable terminal result and do not display a reconnect notice or alter reconnect accounting; transient failures retain bounded recovery.
- A command schedule can invoke the packaged channel CLI after a dynamically bound service start, in both authenticated and unauthenticated modes, without hard-coded ports or leaked credentials.
- A successful turn has exactly one final user-visible delivery, with its completion state attached to that delivery; cancellation, delivery failure, and no-final-output cases have explicit behavior.

## P1: desirable but non-blocking

- #4911 and #4912: migrate Claude/Pi/DSH and add `skills doctor` after Codex registry behavior is proven.
- #4929: schedule-mode guidance.
- #4900: harness-specific declarations for interactive tools.

These improve discoverability once the registry is stable, but must not delay a release that makes skill resolution and terminal delivery reliable.

## Release gate

Before tagging, require build, type-check, lint, and focused regressions for every P0 acceptance criterion. Retain the installed-package matrix and release-candidate verification established by 0.5.1/0.5.2. The release is blocked by any cross-harness manifest divergence, trust-boundary bypass, false reconnect for a persistent error, dropped terminal delivery, or command schedule that cannot reach the current managed service endpoint.
