# Disclaude 0.6.18: waiting for Notebook runs and incremental stdout

Release preparation, 2026-11-06. This patch release packages the reviewed
runtime at main `403adebb1`, which adds one scoped change to the release
baseline: the Jupyter `execute`/`status` wait primitive and the incremental
`notebook_status` stdout cursor (#5320; #5701). Release preparation changes
only version metadata and documentation beyond that scoped change. The final
source commit, archive, checksums, and fresh installation results are
recorded in the release assets.

## Changes

- Jupyter `execute` and `status` can now wait for a run inside one turn, and
  `notebook_status` reports stdout incrementally (#5320; #5701).
  `--wait` blocks until the run reaches one of the four terminal states
  (`completed`, `failed`, `cancelled`, `rejected`); `--timeout S` bounds the
  wait (default 600 seconds, fractional values allowed, at most 86400) and
  requires `--wait`. A wait timeout stops only the CLI wait — it returns the
  last observed state with `wait:{state:"timeout",runPreserved:true}` and a
  hint to query the same `runId` again, and the loop only ever calls
  `notebook_status`, never stop or interrupt. Ambiguous `unknown` or lost
  connection observations keep polling until the timeout instead of guessing
  a terminal outcome, and `wait.state` distinguishes completion from a wait
  timeout.
- `notebook_status` gains an incremental `stdout` view. Without
  `stdoutCursor` the first query keeps the new-session tail semantics
  (bounded tail of the accumulated stream output); passing back
  `stdout.nextCursor` returns exactly the bytes produced after that cursor
  for the same run, with `scope: "delta"`, no duplicates and no gaps, and
  re-querying with the same cursor is idempotent. Cursors are run-scoped
  (`invalid_stdout_cursor` for a cursor from another run or a malformed
  value), a retained stream that no longer covers the cursor reports
  `scope: "reset"` with `resetReason` and re-sends the tail rather than
  silently duplicating bytes, and a single delta above the 100,000-character
  cap trims from the front and reports `skippedBytes`. The wait loop carries
  `nextCursor` across polls, so each poll returns only new output.
- Long waits no longer hold the Project CLI lock. The wait loop leaves the
  fail-closed `withNotebookLock` while sleeping: the initial query stays
  inside the lock, each poll takes a brief lock of its own, and the sleep
  happens outside, so concurrent commands in the same Project (status,
  follow-up execute, stop) keep working during a long `--wait`. The poll
  function is injectable, so existing callers keep their behaviour.
- The Jupyter skill documents the long-run watcher contract (#5320): submit
  `execute` without `--wait`, then arm at most one background
  `status --wait --timeout 86400` watcher for the same `runId`; the harness's
  existing background-task notification delivers its exit exactly once, a
  timeout is the only reason to re-arm, and two live watchers on one `runId`
  would produce two notifications.

## Install and use

Requires Node.js 20+, npm 10+, and Git. After the release is published:

```sh
npm install -g "github:hs3180/disclaude#v0.6.18"
disclaude --version
```

Existing 0.6.17 deployments keep their configuration, registry and
workspace data; stop the running service before upgrading and run
`disclaude start` afterwards. Installation does not touch configuration or
workspace data. Use the [installation/rollback guide](git-install.md) to
switch releases; the prior package remains installed for rollback.

Automated coverage does not replace real-environment acceptance: incremental
stdout on a live remote Jupyter server that is still producing output, and
the one-notification background watcher on a real long-running kernel
execution, remain outside the automated test scope (the full chain is
covered against a mocked server) and should be verified in your own
environment.
