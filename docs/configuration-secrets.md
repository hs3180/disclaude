# Named agents and external secrets

The public configuration has one runtime entry point: `agents.<name>` binds a
backend to `llms.<name>`, which owns its model, API protocol, endpoint and
credential reference. Multiple runtimes can bind different connections for the
same backend. API protocols describe wire formats, not model vendors. Exactly one
`default: true` marker is accepted; the reserved `default` name or first entry is
the documented fallback. Native Codex bindings may omit their model to use the
native account default. No top-level `agent`, `glm`, `anthropic` or `deepseek`
fallback is consulted. See [agent configuration](agent-configuration.md).

## Secret inventory and projection

| Setting | YAML representation | Runtime consumer |
| --- | --- | --- |
| LLM API key | `llms.<name>.api.apiKey: $NAME` or `${NAME}` | Selected runtime's API adapter only |
| Native/tool token, password, private/access/API key | `llms.<name>.env.VARIABLE: $SOURCE` | Selected LLM's runtime/tools only |
| Feishu app secret, verification token, encryption key | Whole external reference under `channels.feishu` | Host channel client only |
| Ruliu app secret, verification/encryption keys | Whole external reference under `channels.ruliu` | Host adapter only |
| REST bearer | `channels.rest.authToken: $NAME` | Host REST server only |
| Service channel-control bearer | Generated by the service; optional explicit service CLI override | Agent channel-delivery integration |
| Public app identifiers, models, endpoints, timeouts, native model aliases | Literal public values | Relevant component |

Global YAML `env` accepts public defaults. Secret-like names (`TOKEN`, `SECRET`,
`PASSWORD`, `PASS`, `API_KEY`, `ACCESS_KEY`, `PRIVATE_KEY`, `AUTHORIZATION`,
`COOKIE`, `CREDENTIAL` components, plus `PGPASSWORD`), credential-bearing URLs and all
explicit model credential source names, must be removed from this section even
when an inherited variable would override them. Native LLM secret settings must
use whole external references. Reference syntax never executes shell expressions.
Application-specific secrets with opaque names still belong in the external
store; use explicit native LLM references to select their consumers.

Inherited secret-like variables and every configured credential/reference source
are masked before the selected LLM's environment is projected. Selected API keys
and endpoints then override conflicting inherited/native settings. Source variable
names, other agents' keys, channel credentials and the secret-file path are not
automatically passed into model children. The channel-control bearer is an explicit
exception required for delivery. This is an environment boundary; filesystem/tool
permissions govern access to local files. Agent-owned workspace `.runtime-env`
keeps its existing lifecycle and is outside this persistent-configuration migration.

For example, grant a notebook-capable LLM its tool credential explicitly:

```yaml
agents:
  analysis:
    backend: claude
    llm: analysis
    default: true
llms:
  analysis:
    model: glm-5.3
    api:
      protocol: anthropic
      baseUrl: https://your-api.example
      apiKey: $ANALYSIS_API_KEY
    env:
      JUPYTERLAB_HOST: https://your-jupyter.example
      JUPYTERLAB_PASS: $NOTEBOOK_PASSWORD
      ANTHROPIC_DEFAULT_HAIKU_MODEL: your-small-model
```

Only that selected LLM receives `JUPYTERLAB_PASS`; `NOTEBOOK_PASSWORD` is not
inherited under its source name. A dormant binding needs no live secret. Selecting
a binding with a missing or explicitly empty API/native reference fails preflight
with its field path and variable name, preserving the existing chat session.

## Sources, deployment and migration

Set `DISCLAUDE_SECRET_ENV_FILE` to an absolute external file before starting the
public service CLI. The file loads before configuration imports, fills only unset
variables, and never overrides an inherited value (including an empty value).
There is no automatic `.env` discovery. The file must be regular, owned by the
service UID and owner-only (`0600` or `0400`), at most 1 MiB; symlinks, FIFOs and
directories are rejected. Parsing is atomic and does not interpolate or execute.
Keep its directory private and outside the workspace/repository.

CLI and local development can set the file path for `disclaude start` or
`node bin/disclaude.js start`. macOS LaunchAgent and Linux systemd set only that
path in their environment; systemd may instead inject an owner-only
`EnvironmentFile`. Docker/Compose mount an owner-only file read-only with the
container service UID, or use the platform's environment secret injection. CI uses
its secret store for the service step. Concrete examples and file syntax are in
[channel credentials](channel-credentials.md#cli-and-deployment); the same loader
handles model and tool secrets as well as channels. Do not put values in YAML,
image layers, command arguments, plist/unit definitions or shared test output.

For the 0.6.4 contract, obsolete top-level provider/singleton sections and inline
secrets fail with migration guidance; there is no silent compatibility fallback.
The application never rewrites configuration files. Before upgrading:

1. Keep a private backup of the original config and service definition. Preserve
   workspace data and the working release for rollback.
2. Move each runtime to `agents`, its model/connection to `llms`, and platform
   settings to `channels`. Replace inline secrets with whole references. Remove
   those values from global YAML `env`; select required tool/native credentials
   through the appropriate LLM's `env` references.
3. Put values in the external secret source, check UID/mode, then validate with
   an isolated channel-disabled startup before changing a live service.
4. During a service window, stop the original connection, start the candidate
   with the preserved workspace and verify the selected runtime, channel health
   and real delivery. Restore the original definition/version if acceptance fails.

Config exports retain references. Model and channel reference values are redacted
in serialized logs, strings/stacks and user-facing diagnostic text. Errors describe
paths and missing variables; they do not print source excerpts or secret values.
An isolated startup or mock endpoint proves deployment wiring, not external
credential validity or a real model/channel interaction. Record those separately.
